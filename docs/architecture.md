# 수리온 MVP 구조

## 목표

첫 버전은 “견적을 빨리 받는 서비스”보다 “같은 고장 사례를 쉽게 찾고 공개 대화로 원인을 좁히는 커뮤니티”를 검증한다. 웹을 먼저 출시하지만 도메인 규칙과 입력 계약을 별도 패키지로 분리해 후속 앱에서도 같은 규칙을 재사용할 수 있게 했다.

## 경계

- `apps/web`: 화면, 라우팅, 데모 상태, Supabase 연결부
- `packages/domain`: UI와 데이터베이스에 종속되지 않는 업무 규칙
- `packages/contracts`: API 요청의 런타임 검증
- `packages/config`: 서비스명, 로고 경로, 브랜드 색상
- `packages/ui`: 향후 웹과 앱이 공유할 수 있는 UI 진입점

API는 처음부터 `/api/v1` 아래에 둔다. 현재는 환경 변수가 없으면 안전하게 데모 응답을 반환하고, Supabase가 연결되면 동일한 입력 계약을 사용해 실제 테이블에 기록한다.

## 데이터 흐름

1. 홈과 검색은 사례 목록을 빠르게 탐색한다.
2. 질문은 제품·모델·증상 정보를 구조화해 사례로 생성한다.
3. 모든 역할의 답변은 한 개의 시간순 댓글 흐름에 쌓이며 작성 당시 역할을 보존한다.
4. 충분한 공개 답변만 유효한 전문가 답변으로 인정한다.
5. 질문자는 유효 답변을 남긴 수리 가능 전문가에게만 비공개 요청을 보낸다.
6. 질문자가 해결 결과를 등록하면 사례가 검색 가능한 해결 지식으로 남는다.

## 데모와 실제 서비스

데모 상태는 `localStorage`에 저장해 로그인·서버 없이도 전체 흐름을 평가할 수 있다. 실제 서비스 전환 시에는 Supabase Auth, Storage, Realtime을 연결하고, 데이터 권한은 SQL의 RLS 정책과 서버 API에서 이중 확인한다. 관리자 권한, 전문가 인증 상태, 수리 가능 여부는 일반 프로필 수정으로 변경할 수 없도록 분리한다.

## 앱 확장

앱은 Expo/React Native를 별도 애플리케이션으로 추가하는 방식을 권장한다. `domain`, `contracts`, `config`는 그대로 공유하고, 웹 전용 DOM 컴포넌트와 앱 네이티브 컴포넌트는 분리한다. 이를 통해 업무 규칙이 플랫폼별 화면 구현에 섞이는 것을 막는다.
