# 수리온 MVP 구조

## 목표

첫 버전은 “견적을 빨리 받는 서비스”보다 “같은 고장 글을 쉽게 찾고 여러 사람이 공개 댓글로 원인을 좁히는 커뮤니티”를 검증한다. 한 사람의 글을 대표 사례로 만들기보다 개별 질문과 경험이 계속 쌓이는 구조를 우선한다. 웹을 먼저 출시하지만 도메인 규칙과 입력 계약을 별도 패키지로 분리해 후속 앱에서도 같은 규칙을 재사용할 수 있게 했다.

## 경계

- `apps/web`: 화면, 라우팅, 데모 상태, Supabase 연결부
- `packages/domain`: UI와 데이터베이스에 종속되지 않는 업무 규칙
- `packages/contracts`: API 요청의 런타임 검증
- `packages/config`: 서비스명, 로고 경로, 브랜드 색상
- `packages/ui`: 향후 웹과 앱이 공유할 수 있는 UI 진입점

API는 처음부터 `/api/v1` 아래에 둔다. 현재는 환경 변수가 없으면 안전하게 데모 응답을 반환하고, Supabase가 연결되면 동일한 입력 계약을 사용해 실제 테이블에 기록한다.

게시판 이름과 식별자는 하나의 카테고리 원본에서 읽고, 화면에서는 공용 게시판 선택 컴포넌트를 사용한다. 전체글·검색·글쓰기의 데스크톱 목록과 모바일 선택 상자는 동일한 `board` 값과 주소 생성 규칙을 공유한다. 즐겨찾기 ID 목록은 계정 상태에 별도로 저장하므로 현재 게시판을 나타내는 `board` URL을 바꾸지 않으며, 표시할 때만 즐겨찾기 그룹을 원본 순서 그대로 앞에 배치한다.

## 데이터 흐름

1. 홈, 검색, 제품별 게시판은 독립된 사용자 게시글 목록을 빠르게 탐색한다.
2. 질문과 경험 글은 제품·모델·증상 정보를 구조화해 생성한다.
3. 모든 사용자의 댓글은 유형 선택이나 의견 딱지 없이 한 개의 시간순 공개 대화에 쌓인다.
4. 역할 스냅샷은 권한과 안전 판정을 위해 내부에 보존하되, 댓글의 우열이나 채택 표시에 사용하지 않는다.
5. 충분한 공개 댓글을 남긴 인증 전문가만 수리 요청 대상이 될 수 있다.
6. 글쓴이가 해결 결과를 등록하면 특정 댓글과 독립된 해결 기록으로 남는다.
7. 같은 제품·모델·증상의 글은 원문과 작성자를 유지한 채 나중에 탐색용으로 묶을 수 있다.

## 데모와 실제 서비스

데모 상태는 `localStorage`에 저장해 로그인·서버 없이도 전체 흐름을 평가할 수 있다. 실제 서비스 전환 시에는 Supabase Auth, Storage, Realtime을 연결하고, 데이터 권한은 SQL의 RLS 정책과 서버 API에서 이중 확인한다. 관리자 권한, 전문가 인증 상태, 수리 가능 여부는 일반 프로필 수정으로 변경할 수 없도록 분리한다. 프로필 사진은 선택 입력으로 두고 미등록 계정에는 중립적인 기본 아바타를 사용한다. 접속 여부나 마지막 활동 시각은 공개 응답에 포함하지 않는다.

## 인증 구조

- 브라우저는 Supabase Auth의 카카오 OAuth와 이메일 OTP를 사용한다. 비밀번호는 수리온이 직접 수집하거나 저장하지 않는다.
- OAuth 시작 전과 콜백에서는 PKCE·state 검증을 Supabase 인증 흐름에 맡기고, 콜백에서 발급된 세션은 Supabase SSR 쿠키로 유지한다. 운영 인증은 HTTPS에서만 제공하며 인증 세션이나 토큰을 데모 `localStorage` 상태에 넣지 않는다.
- 서버 콜백은 인증 코드를 세션으로 교환한 다음 내부 상대 경로로만 이동한다. 요청의 `next` 값은 공용 안전 검사기를 거치며 외부 주소는 `/my/questions`로 대체한다.
- 인증 설정이 없는 개발 환경에서는 카카오나 인증번호 요청을 성공한 것처럼 처리하지 않는다. 사용자가 이해할 수 있는 설정 안내를 반환하고, 공개 커뮤니티 열람과 기존 데모 데이터 검수는 계속 가능하게 둔다.
- 이메일 인증번호의 만료, 재전송 제한, 시도 횟수 제한은 Supabase Auth 설정을 기준으로 하고 클라이언트의 카운트다운은 안내용으로만 사용한다. 성공 판정과 제한을 브라우저 상태만으로 결정하지 않는다.
- 최초 인증 직후에는 가입 완료 화면에서 닉네임과 필수 동의를 검증한다. 카카오 신규 사용자와 이메일 인증을 마친 신규 사용자는 모두 `POST /api/auth/profile`로 이 값을 서버에 전달한다. `profiles` 생성과 약관 동의 기록은 같은 서버 경계에서 처리해 필수 정보 일부만 저장된 공개 계정이 생기지 않게 한다.
- 선택한 프로필 사진은 브라우저의 파일 확장자만 신뢰하지 않고 서버에서 JPG·PNG·WEBP 시그니처와 디코딩 후 2MB 제한을 확인한다. 검증한 사진은 EXIF·위치 메타데이터가 남지 않도록 512px WebP로 다시 인코딩한 뒤 사용자 ID 아래 `avatars/{userId}/avatar` 객체로 올리고, `profiles.avatar_path`에는 경로만 저장한다. 사진 검증·처리·업로드가 실패하면 가입 결과와 분리된 경고를 반환해 프로필 설정에서 다시 시도하게 한다.
- 공개 API의 작성 권한은 화면의 로그인 표시가 아니라 서버가 검증한 `auth.uid()`와 RLS로 판정한다. 인증 실패는 `401`, 권한 부족은 `403`으로 구분한다.
- 인증 설정이 연결된 환경에서는 글쓰기와 마이페이지·저장·알림·수리 요청·전문가·관리 화면을 서버에서 보호한다. 비로그인 사용자는 안전한 `next`를 포함한 로그인 화면으로, 인증만 하고 가입을 마치지 않은 사용자는 프로필 완료 단계로 이동한다. 인증 설정이 없는 데모 환경에서는 기존 화면 검수를 위해 이 리디렉션을 적용하지 않는다.

### 인증 검증 범위

외부 카카오와 실제 메일 발송을 E2E 테스트에서 호출하지 않는다. 로컬 자동 검증은 다음 경계를 확인한다.

1. 인증 환경 변수가 없을 때 명시적인 설정 오류를 표시하고 로그인 성공으로 이동하지 않는다.
2. 이메일 형식, 6자리 인증번호, 필수 약관과 만 14세 이상 확인을 UI에서 검증한다.
3. 카카오·OTP 성공 응답은 테스트에서 네트워크 경계를 가로채 가입 완료 화면만 검증한다.
4. 외부 또는 프로토콜 상대 복귀 주소가 `/my/questions`로 정규화되고, 정상 내부 복귀 주소는 유지된다.
5. 실제 카카오 리디렉션, 이메일 전달률, 쿠키 보안 속성, RLS는 별도의 배포 전 통합 검수에서 확인한다.

## 앱 확장

앱은 Expo/React Native를 별도 애플리케이션으로 추가하는 방식을 권장한다. `domain`, `contracts`, `config`는 그대로 공유하고, 웹 전용 DOM 컴포넌트와 앱 네이티브 컴포넌트는 분리한다. 이를 통해 업무 규칙이 플랫폼별 화면 구현에 섞이는 것을 막는다.
